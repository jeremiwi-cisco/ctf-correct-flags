01 · The workflow

One report. A verified mission.

The same original correction process, with an artifact path explicitly supplied for every invocation.

Every run starts with a path check. If you did not supply a path for this invocation, the agent asks: “What is the full path to the completed check-flags artifact for this run?” It never picks a remembered, default, or discovered report for you.
  1. 01
    Step 1 of 7Where · Agent conversation

    Provide this run’s inputs.

    Share the full artifact path and exact Cisco CTF mission name with the skill invocation. If either is missing, the agent asks for it. A name already supplied during this task satisfies the mission requirement.

    Ready when: the artifact path was explicitly supplied for this run.

  2. 02
    Step 2 of 7Where · Local artifact

    Inspect the report.

    The agent reads the completed check-flags artifact, preserves a snapshot and SHA-256 hash, and identifies all PASS, CHANGED, and ERROR rows. The report stays in its existing format. Missing, conflicting, or duplicate data needs resolution.

    Ready when: the report’s identity, contents, and coverage are understood.

  3. 03
    Step 3 of 7Where · Your existing Chrome session

    Confirm the exact mission.

    The agent checks authentication and creator access at play-security.ciscoctf.io, then verifies the named mission in content management. It compares the report with history scoped by portal origin, mission UUID, and tenant.

    Ready when: the mission heading and stable identity match the intended target.

  4. 04
    Step 4 of 7Where · Mission flag editors

    Process every report row.

    Match each flag by its question and stable UUID as well as its displayed number. Every status has a different purpose.

    PASS

    Audit the live answer.

    Read the stored regex and case setting. Compare them with the verified baseline. A suggested alternative alone does not authorize an edit.

    Continue to portal tests →

    CHANGED

    Enter the suggested regex.

    Record the live before value. Transfer the artifact’s Suggested Regex into Expected Flag (Answer), preserving the documented escaping.

    Continue to portal tests →

    ERROR

    Record incomplete coverage.

    Preserve the previous baseline. Report missing or failed source evidence; do not invent an answer or correction.

    Include in the final report →

  5. 05
    Step 5 of 7Where · Portal answer tester

    Validate the answer behavior.

    Test the exact Actual Value and every stored durable acceptance/rejection example. Read the portal’s feedback for each test. A proposed correction must pass every required test before saving; a local regex check alone is insufficient.

    Failed test? Record the result and cancel the unsaved correction.

  6. 06
    Step 6 of 7Where · The same flag’s editor

    Verify persistence.

    For CHANGED rows, Save once, inspect the flag-specific success message, and reopen the editor to verify the exact stored regex and unchanged case setting. Close verification with Cancel. If the intended regex is already stored, test and log it as already applied.

    PASS audit → CancelCHANGED → Save → Reopen → Verify → Cancel
  7. 07
    Step 7 of 7Where · Local run folder and journal

    Record the evidence.

    Save a per-flag report, observations, tests, and screenshot evidence. Append the change log using the prepare-time source hash. Advance the baseline only from eligible verified evidence; failed or unexplained drift retains the previous good baseline.

    Complete when: correction outcomes, PASS coverage, and unresolved issues are explicit.

02 · Read the handoff correctly

Pattern and test answer are separate.

The artifact keeps its original format. Its values play distinct roles in the portal.

What each report field means

FieldHow the skill uses it
Actual ValueThe concrete answer entered into Test Flag (Answer).
Suggested RegexThe expression entered into Expected Flag (Answer) for CHANGED rows.
Expected PatternThe source report’s expected expression. The live editor supplies the actual before value.
ID + QuestionSource identity clues, confirmed against the mission’s live flag UUID, title, and number.
Status + NotesDetermine correction/audit scope and identify source issues.
SYNTHETIC CHANGED EXAMPLE

Two values. Two fields.

The suggested expression belongs in the expected answer field. The observed answer belongs in the tester.

EXPECTED FLAG (ANSWER)^Example;\s?39$← Suggested Regex, with known display escaping decoded once
TEST FLAG (ANSWER)Example; 39← Exact Actual Value from the report

Synthetic illustration only. A changing count such as 39 does not become a permanent policy example. Regex alternation pipes and literal backslashes must survive transfer intact.

03 · Explore the decisions

A source PASS still needs a live audit.

Choose a status to see the expected outcome. These examples do not connect to a report or portal.

Audit what the portal actually stores.

PASS means the source pattern accepted the observed answer. Read and test the live portal pattern against the baseline and durable examples. Keep the last good baseline if unexplained drift or a failing test appears.

Outcome: audited and closed with Cancel; no routine answer edit.

04 · Evidence and boundaries

The result is more than a saved regex.

The run report distinguishes verified changes, already applied answers, failures, and saved but unverified outcomes.

What stays on disk

The original storage default is retained. Verified history is scoped to portal origin, mission UUID, and tenant.

├── state/
│   ├── change-log.jsonl  # append-only events
│   └── baseline.json     # verified state projection
└── <timestamped-run>/
    ├── source snapshot + SHA-256
    ├── observations + test results
    ├── per-flag report
    └── screenshot evidence

First run for a missionEstablish a baseline from confirmed live identity and successful portal tests.

Later runs for the same missionCompare with its verified baseline and retest stored acceptance/rejection examples.

A different missionIts UUID and tenant scope keep its rules separate. No personal history is bundled with this skill.

When the agent stops a flag

  • Mission or flag identity is ambiguous.Resolve the target or numbering mismatch before writing.
  • A suggested expression fails validation.Recheck transcription/escaping once. Cancel if it still fails; report the supplied pattern and answer.
  • Existing policy examples fail.Do not save a behavioral regression or silently remove accepted variants.
  • Save completion is uncertain.Inspect the stored value before retrying. Dialog closure alone does not prove persistence.
  • The session expires.You handle login in Chrome. The agent inspects the affected flag before resuming.

Question text, hints, points, visibility, answer type, and case sensitivity retain their existing values. Independent, unambiguous flags can continue when one flag has a problem.
